# WireFlow — Implementation

WireFlow is a tool for building wireframes and clickable prototypes: pages are drawn in the Designer, linked to each other through element hyperlinks (`Href`), and clicked through in the Browser.

## Products

| Product | Project | Role |
|---|---|---|
| WireFlow Designer | `WireFlow.Designer` | WPF editor with a docking UI (OptimaxTools.Dock): pages, layouts (master pages), parts, images, outline, properties. |
| WireFlow Browser | `WireFlow.Browser` | WPF viewer: opens a `.wf` project, shows its `Home` page and follows `Href` clicks with back/forward history. |

Shared projects:

| Project | Role |
|---|---|
| `WireFlow.Types` | The DOM, the data model (`FlowProject`, `FlowPage`, `FlowLayer`, `FlowElement`, `FlowImage`, `FlowGroup`, `FlowStack`, `FlowPart`), and the `IFlowRepository` interface. It uses no WPF type (the project does not use WPF): alignments, text wrapping, font stretch, image stretch and a stack panel's direction are its own values (`FlowValues.cs`), with WPF's names and numbers, which are what the files hold. Core's `WpfValues` converts them for the WPF presentation (`ToWpf`, `ToFlow`). |
| `WireFlow.Core` | `WireFlowEngine` (renders the model to WPF controls and serializes them back), `DesignerPanel`, outline wrappers, grids. |
| `WireFlow.Repository.Sqlite` | `SqliteRepository`, the storage in use: a project in one SQLite database file (`.wf`). Converts folder projects (`.project`) into `.wf` files. |
| `WireFlow.Repository.Folder` | `FlatFolderRepository`, the earlier storage: a project as a folder. Read when a folder project is converted; its `SerializeToJSON` and `DeserializeFromJSON` are the JSON settings of both storages. |
| `WireFlow.Repository.Archive` | `ZipArchiveRepository`, an unimplemented stub. |
| `OptimaxTools.Wpf.PropertyGrid` | The Designer's property grid, WireFlow's own: `OptimaxTools.Wpf.PropertyGrid` (see "Property grid"). XAML namespace `http://schemas.optimax.com/wpf/xaml/propertygrid` (prefix `pg`). |
| `OptimaxTools.Dock`, `OptimaxTools.Dock.Core` | The docking layout system of the Designer: the `AvalonDock` and `AvalonDock.Core` components of Dirkster.AvalonDock 5.0.1, an MS-PL fork of Xceed's AvalonDock, renamed to the `OptimaxTools.Dock` namespaces. XAML namespace `http://schemas.optimax.com/wpf/xaml/dock` (prefix `dock`), also mapped into WPF's presentation namespace, as upstream does. Strong-named with WireFlow's `OptimaxTools.Dock\sn.snk`. `LayoutGridControl` gives the splitters between panes the manager's splitter styles only when they are set; upstream set a null `Style`, which hid the theme's splitter style. Its windows with a theme style (`OverlayWindow`, `LayoutFloatingWindowControl`, `NavigatorWindow`) refer to the style of their own type from their constructors (see "Known traps"). |
| `OptimaxTools.Dock.Themes.Metro` | The Metro theme of Dirkster.AvalonDock 5.0.1, renamed, used by the Designer, with WireFlow's two brush colors (`BaseColor5`, `BaseColor6`) in `Brushes.xaml`, and in `Theme.xaml` themed backgrounds for the document pane and the Ctrl+Tab navigator window, which upstream draws white, and splitters drawn as a rail with 1 px borders (`AvalonDock_ThemeMetro_SplitterBorder`) inside their 5 px grab area. |

## Development environment

- .NET 10, target framework `net10.0-windows`, WPF (`UseWPF`). All projects are SDK-style.
- Visual Studio 2026 (18.x) with the .NET 10 SDK. The solution file is `WireFlow.slnx`, the XML solution format; it lists the projects only, as they all use the default Debug and Release configurations for Any CPU. ReSharper's settings are in `WireFlow.slnx.DotSettings`.
- NuGet packages are `PackageReference` items restored to the NuGet global packages folder. The `packages/` folder at the root is left over from `packages.config` and is not used by the build.
- Each project declares its assembly identity in `Properties\AssemblyInfo.cs`. `Directory.Build.props` turns off the SDK-generated copies of those attributes, so the SDK only adds the ones the files lack, such as `SupportedOSPlatform`.

## Application icons

`WireFlow.Designer\Designer.ico` (white WF mark on a red tile, as in `Documents\logo.png`) and `Browser\Browser.ico` (red WF mark on a charcoal tile with a gray rim) are the projects' `ApplicationIcon`s. `Documents\make-icons.ps1` draws them on a whole-pixel grid at 16–256 px; change the script and run it again rather than editing the `.ico` files. The Designer's main window sets its own title-bar icon, `Views\logo.png`; the Browser's windows use the application icon.

## Themes

The Designer and the Browser have the themes of Optimax's other programs (PDFTools): View → Theme offers System, Light, Dark and Classic, kept in each program's settings (the Designer's `ConfigSettings.Theme`; the Browser's `BrowserSettings.Theme`, in `%APPDATA%\WireFlow\WireFlow.Browser.config`; anything else is System). They come from `MaxServices.Core` 1.1.0, Optimax's own library made in Optimax.Shared.Lib, kept as a package in `LocalPackages\` and found through `nuget.config`. Its `AppTheme` swaps the first dictionary of `App.xaml` (WPF's Fluent light or dark, or Core's classic) and puts its palette after it.

- `DesignerTheme` applies a choice and keeps the Designer's own brush keys (`ListBackgroundBrush`, `LightLightColorBrush`, `DesignerBackgroundBrush` and the others it lists) and the Metro theme's base colors and splitter border (the palette's `ChromeBorder`, which PDFTools uses for its pane grips) in the application's resources as the palette's brushes for the current theme. XAML uses those keys by `DynamicResource`, and code by `SetResourceReference`, so that a change of theme reaches them.
- The Browser's XAML uses the palette's keys (`Palette.AppBackground`, `Palette.PaneHeader` and others) by `DynamicResource` directly; it has no brush keys of its own to map.
- Neither program has implicit styles for standard controls (menus, list boxes, tree views, splitters): one would hide Fluent's style, and Classic has no Fluent style to base one on. `EditableListBox`, a type of its own that the theme's `ListBox` style does not reach, has one that sets only colors and fonts. The Tools list and the Outline set the same `Background` (`ListBackgroundBrush`) themselves, so that the three panes look alike in every theme.
- The page and what is drawn on it keep their own colors; the area around the page follows the theme (the palette's `PreviewBackground`). `DesignerPanel` draws a 1 px frame just outside the page in the palette's `PageFrame`, as PDFTools frames its pages, so that the page shows whatever its color; the frame follows zoom and pan. A new project's page background is `FlowProject.DEFAULT_BACKGROUND`, `#555`: a gray that differs from the area around the page in every theme (`#333333` in Dark, `#CCCCCC` in Light and Classic) without glaring in Dark. Both storages and Core's `Constants.DEFAULT_BACKGROUND` (the Browser's fallback for a color it cannot read) use it.
- Fluent's menus and toolbars are taller than the old ones: give the rows that hold them `Auto` height rather than a fixed one.
- Fluent pads list items by 12 px, 45 px rows. To make a list compact without losing the theme's item template, set the containers' `Padding` as a local value, as `MainDesignerWindow.CompactRows` does for the lists in `CompactLists`, Tools, Pages, Layouts, Parts, Images and History (27 px rows, as a Fluent menu item), as each list makes its rows and when the theme changes; Classic's own padding is already compact, so it is left there. An `ItemContainerStyle` would replace the theme's style, and one `BasedOn` it would keep the style of the theme current when it was loaded.

## Property grid

`OptimaxTools.Wpf.PropertyGrid` lists the browsable properties of `SelectedObject`'s type, as Xceed's grid did: by category (in the order of their names) or by name, with a filter box, a header naming the object's type (the class name an object that describes itself gives, `ICustomTypeDescriptor.GetClassName`: `NodeProperties` names the node's kind, "Rectangle", "Stack Panel", "Page", or "3 objects") and `Name`, and a name column whose width the grip between the columns sets. Rows are virtualized, grouped or not. Up and Down move the keyboard focus to the value of the row above or below, across categories, scrolling a row out of view into it (`PropertyGrid.OnPreviewKeyDown`); a value typed is set as its box loses the focus. An open drop-down list, and a text box of several lines while its caret has a line to go to, keep the keys.

- `PropertyItem` is one property. Text goes through the property's `TypeConverter` in the invariant culture, as in XAML (`Auto`, `1,2,3,4`, `#FFFF0000`); empty text is null for a reference type other than string. A value that cannot be set leaves the property and sets `Error`, which the row shows as a red frame and a tooltip. While listed, each item watches its property (`AddValueChanged`), so a change made elsewhere shows; the watch ends when the selection changes.
- `PropertyValueChanged` is raised for a value set in the grid only, and only when it changed. Xceed's was raised for any change of a watched property, so it fired on every click; the Designer sets `IsModified` from it.
- `PropertyEditors` chooses each property's editor, as Delphi's `RegisterPropertyEditor` does: a registration names a property type (which also matches derived types), optionally narrowed to a type of object and a property name; the most specific matching registration wins, and the latest of equals. Without one: read-only text for a read-only property; a check box for a Boolean; a swatch with text for a brush or a color; a list of the system's fonts for a font family; a list for an enum, a font weight, style or stretch, or a converter's closed list of values; text otherwise. A `PropertyEditor` creates one control per row shown.
- An editor with a dialog (`HasDialog`, as Delphi's `paDialog`) gets a "…" button at the right end of the value, which, as Ctrl+Enter in the value, calls its `ShowDialog`; a value typed but not yet set is set first. The editor sets the value chosen with `PropertyItem.SetValue`, which raises `PropertyValueChanged`. A read-only property has no button.
- The Designer registers `ColorPropertyEditor` (in `App.Application_Startup`) for every `Brush`, `Color` and `Color?` property: the grid's swatch and text, and a dialog, `Views\ColorPickerDialog`, the color dialog of Optimax's other programs (MarkdownTools' MaxPad, PDFTools) on PixiEditor.ColorPicker. A brush property gets a solid brush; a gradient or image brush starts the dialog from white. MaxServices.Core has no color dialog, so the Designer has its own copy. Unlike MaxPad's, it has no second color to swap with; under the pickers it has swatches, black, white, light gray (`#DDDDDD`) and gray (`#999999`), and the last ten colors chosen with OK (`ColorPickerDialog.RecentColors`, the latest first, kept in `ConfigSettings.RecentColors`); a click on one makes it the color. PixiEditor's sliders fix their number fields at 40 x 18 px, which Fluent's text box (its least width and padding, and its border and inner margin, which left too little height for the text) overflowed: the dialog gives the sliders a text box style of their own, based on the theme's, without the least size and with less padding, which, as each field loads, lets it take the height its text needs (the template's height outranks a style's).
- The Designer registers `LayoutPropertyEditor` (in `App.Application_Startup`) for a page's or layout's Layout: an editable list of the layouts (see "Page keys and names").
- The Designer registers `FontPropertyEditor` (in `App.Application_Startup`) for the FontFamily of texts and boxes (their nodes' `Font`): the name as text, and a dialog, `Views\DesignerFontDialog`, the font dialog of MarkdownTools' programs (MaxPad, MaxWrite), `OptimaxTools.FontSelection` 1.1.0, Optimax's own library made in MarkdownTools, kept as a package in `LocalPackages\` as MaxServices.Core is; it has no look of its own, and the Designer's subclass gives it the Designer's dialog colors. It opens on the element's family, size (pixels, as `FontSize` is: a unit of 1 pixel) and face, and OK sets `FontSize`, `FontWeight`, `FontStretch`, `FontStyle` and, last, the family, each through its own row (`SetComponentProperty`); with several elements selected, a value they do not share opens empty (the family as Segoe UI), and each gets the font chosen. A text's or box's `FontStyle` (`FlowFontStyle`: Normal, Oblique, Italic, as WPF's `FontStyles`) is its node's own; a file written before it has none and reads as Normal.
- The row with the keyboard focus is highlighted across its whole width (`HighlightSelectedRow`, on by default) in `SelectedRowBackground`, or, without one, in the grid's `Foreground`, faint. The Designer gives it the Windows accent color (`SystemColors.AccentColor`) at alpha `0x60`, which shows on light and dark grids alike and differs from the gray of the category headers, or the color chosen in Tools → Options (`MainDesignerWindow.ApplyPropertyHighlight`).
- The template gives `TextBox`, `CheckBox`, `ComboBox` and `ComboBoxItem` implicit styles of its own, inside the grid only: compact (22 px rows; Fluent's controls are 32 px tall) and in the grid's `Background` and `Foreground`, in every theme. Highlights and lines are the grid's `Foreground` at a low opacity, so they suit light and dark alike. The Designer sets `Background`, `Foreground` and `CategoryBackground` from its theme brushes.

## DOM

The Flow* classes of `WireFlow.Types` are the DOM: the model of a project, its pages, layouts, parts and their elements, apart from any presentation. Each node (`FlowBase`) tells of each change of its properties (`INotifyPropertyChanged`, once per change; its setters go through `Set`), and knows the node holding it (`Parent`: a layer's page, an element's layer or group), which is neither saved nor shown in Properties. A node's children (a page's `Layers`, a layer's `Elements`, a group's or stack panel's `Children`) are a `FlowNodeCollection`, an `ObservableCollection` that sets and clears their `Parent`; a list set as a whole replaces its content, as the JSON reader may. The DOM uses no WPF type (see `WireFlow.Types` under "Products").

The DOM is the model; WPF is a view of it. The Designer keeps each open page or layout as its DOM (`DesignerNavigator.CurrentPage`, as the repository read it), edits the nodes, and saves the DOM (`SavePage`, `SaveLayout`); the Browser draws the DOM it reads. Neither makes a DOM from WPF elements any more (`SerializePage` is no longer used).

- **The view follows the DOM.** `WireFlowEngine.RenderPage` draws each layer and element and ties it to its node (`FlowView.Node`, an attached property; `FlowView.GetNode` finds an element's node). It then follows the nodes: a change of a node's property brings its element up to date in place (`Refresh`, then `Apply`, which sets every value of the kind from the node), so the WPF element stays the same object and the Designer's selection and adorners stay on it; an image or part reference that names another image or part is drawn again. A change of a page's layers (`FollowLayers`, `ReconcileLayers`) or of a layer's, group's or stack panel's children (`FlowNodeCollection`) draws the nodes added, removes the elements of those taken away and puts the panel's children in the nodes' order (`Reconcile`). The page's size and background follow its node. What the engine listens to is kept on each element (`ViewLink`) and let go when the element is taken away or the page is drawn again (`Unfollow`). Each kind is drawn as `CreateElement` (the control, with the drawings of its children) and `Apply` (its values): a new kind needs both, and its kind in `ConvertUiElement`.
- **A group's size** is the extent of its children (`ApplyGroupSize`), worked out from their nodes whenever a child or the children change; it is not written into the group's node. A stack panel places its children on the page (the view), not in their nodes: their saved positions inside a panel do not matter, as the panel places them again when drawn.
- **Edits go through the DOM.** Every operation of `DesignerNavigator` changes nodes: dragging and the arrow keys, aligning, distributing, stacking and sizing set `Left`, `Top`, `Width` and `Height` (`SetLeft` and the others, which write the element's node); drawing adds the node of the element the tool makes (`WireFlowEngine.ToNode`, so a tool still makes its element with its defaults); duplicating copies a node through its JSON; deleting, grouping, ungrouping and ordering move nodes between and within `layer.Elements` and `group.Children`, after which the Designer selects the elements that show them (`ViewOf`). `ResizingAdorner` writes the sizes and positions it changes into the node too. An operation must not change an element on the page directly: the view would undo it at the node's next change, and saving would not see it.
- **Properties shows the node** (`MainDesignerWindow.CurrentProperties`): `NodeProperties` lists the selected element's node's own properties for its kind, under the names the Designer has shown them by (a text's `StrokeThickness` as `TextPadding`, a box's `Stroke` as `BorderColor`, `VerticalAlignment` as `TextVerticalAlignment`, ...), or the page's node (its size, own or inherited, and its background, empty when it follows its layout or the project) when no element is selected. A value set there sets the node; a change made anywhere shows in the row (`NodePropertyDescriptor` watches the node). A box's or text's `TextHorizontalAlignment` set there carries its `TextAlignment` with it. With several elements selected, Properties shows a `NodeProperties` of all their nodes: the rows that every one of them shows, under the same name and of the same type, but `Name` (`CommonPropertyDescriptor`); a value shows where they all have it and is empty where they differ, and a value set is set on each through its own row, so each node's own rules apply, and Undo takes it back at once. `ColorPropertyEditor` edits the colors kept as text (`Fill`, `Stroke`, `Foreground`, `Background`, `BorderColor`) with the swatch and the color dialog, and writes `#AARRGGBB`.

## Cut, Copy and Paste

Edit → Cut (Ctrl+X), Copy (Ctrl+C) and Paste (Ctrl+V) move elements between pages, layouts and parts, and within one. The page's context menu (`Classes\DesignerContextMenu.xaml`) has the same three commands at its top, before Duplicate and Delete. A text box with the keyboard (in Properties, say) cuts, copies and pastes its own text instead: its own bindings come before the window's.

- **The clipboard holds nodes.** `DesignerNavigator.CopySelectedElements` puts the selected elements' nodes on the clipboard as a JSON array in the format `WireFlow.Elements` (`ClipboardFormat`), each written as it is saved, but at the place it shows on the layer (a child of a group or a stack panel too); an element inside another selected one goes with it, not on its own. `CutSelectedElements` copies, then deletes. Another program sees nothing to paste.
- **Paste** (`PasteElements`) reads the nodes back and adds them to the current layer, where they were copied from, moved down and right by 10 px (`PASTE_OFFSET`) while they would lie exactly on elements of the same kind already there, and selects them. As any edit, it goes through the DOM: it is one step of Undo, and `GiveIds` gives each pasted node an ID of its own, as for a duplicate.

## Undo/Redo

The Designer's Edit → Undo (Ctrl+Z) and Redo (Ctrl+Y, Ctrl+Shift+Z) take back and redo the edits of the page or layout in front, without limit, since it was opened or last saved. A text box with the keyboard (in Properties, say) undoes its own typing instead: its own bindings come before the window's.

- **The history records the DOM.** `FlowHistory` (in `WireFlow.Types`) watches every node of a page's tree: each change of a property (`FlowBase.Set` tells it with the values before and after, `FlowPropertyChangedEventArgs`) and of a list of children (`FlowNodeCollection`, which never resets: `Clear` removes node by node). Undoing applies the changes of a step backwards, in reverse; the view follows the DOM, so it follows undo too. No operation has undo code of its own: every edit made to the DOM, by whatever means, can be undone, Properties included.
- **Steps.** `DesignerNavigator` makes one step of each gesture of the mouse, a drag of the selection (`SelectStart` to `SelectEnd`) or a resize (`ResizingAdorner.ResizeStarted` to `ResizeCompleted`), and of each other edit: its changes are closed into a step when the dispatcher is idle (`ContextIdle`), after the edit and before the next input. An arrow key is a step each.
- **Scope.** Each open page or layout has its own history (`DesignerNavigator.History`), started again whenever `CurrentPage` is set (opening, navigating, reloading) and cleared when the page is saved (`SaveCurrentPage`, `SaveCurrentLayout`, `SaveCurrentPart`). Undo and Redo deselect first, as the elements selected may be taken away. The page is unmodified again once every step since it was opened or saved is undone.
- **A node is recorded only while it is in the page's tree.** An operation must put a node on the page before it changes it: a node changed while out of the tree (a new group being filled, a child between its group and its layer) changes unrecorded, and undoing the steps around it leaves the page wrong. `GroupSelected` therefore puts the new group on the layer before moving the elements into it, and `UngroupNode` puts each child on the layer before placing it.

## Elements

Every element a tool draws is a `BaseDesignerObject`, a `UserControl` with `Left`, `Top` and `Href` (Navigation) whose content is the WPF shape that draws it, built by its constructor: `WireFlowText` (kind `text`, a `WireFlowTextBlock`), `WireFlowRectangle` (`rect`, a `Rectangle`), `WireFlowEllipse` (`ellipse`, an `Ellipse`), `Box` (`box`) and `ImageBox` (`image`). Each forwards the properties of its content that make sense in Properties (`Fill`, `Stroke`, `StrokeThickness`, a text's `Text`, `TextAlignment`, `TextPadding` and others); a text's font, `Foreground` and `Background` are the element's own. The engine chooses the kind from the class's name in `ConvertUiElement` and the class from the kind in `RenderElement`: a new kind of element needs both. Because a `UserControl` reports the events of its content as its own (`e.Source`), a click anywhere on an element comes from the element, which the Navigate tool and selection rely on.

- Links: an `Href` names an `Id` (shown as ID in Properties), that of a page or of an element or layer on one, or the name of a page, and leads to that page: `WireFlowEngine.PageOfHref` looks for a page with that ID, then a page holding it, then a page of that name, reading the pages as the repository gives them (unsaved edits of a page open in the Designer are not seen until it is saved), and the Browser and the Designer's Navigate tool both go through it; a link that names neither leads nowhere. A link keeps what it names: an ID stays an ID and a name a name. IDs and names compare ignoring case. When an ID changes in Properties, or a page's name, the links naming it change with it (`MainDesignerWindow.RetargetLinks`, from `NodeProperties.LinkTargetChanged`): in the documents open, as an edit of each, and in the others through `WireFlowEngine.RetargetLinks`, which saves their drafts; a page's old name is left in links when it is also an ID, which links name first. Every node has an `Id` (`FlowBase`). `FlowIds` makes them: a new page gets one made of its name (`page-2` for "Page 2", `WireFlowEngine.CreatePage`; a new project's first page too, `WireFlowEngine.NewProject`), and an element put on a page or layout without one, or with one another node has (a copy), gets its kind and a number (`rect-3`): `FlowHistory.NodeAdded` tells the Designer of each node an edit adds, and `DesignerNavigator.GiveIds` gives it. An ID is unique in the project: `DesignerNavigator.IsIdTaken` looks in the page as it is, the other documents as the repository has them (`WireFlowEngine.IdsOutside`, read once per page opened), and the IDs given out to other documents not yet saved (`IsIdGivenElsewhere`); Properties refuses an ID typed in that is taken (`NodeProperties.IdTaken`). A new layout gets an ID made of its name too (`WireFlowEngine.CreateLayout`); new parts get none, and layers none. With several elements selected Properties leaves the ID, as it leaves `Name`. `Documents\upgrade-links-to-ids.cs` converted the projects in `Data` from links naming pages: each page got an ID of its name, and each link naming a page by its name that page's ID (`dotnet run upgrade-links-to-ids.cs -- <file.wf> ...`; running it again changes nothing). Every element with an extent can be a hyperlink (`ILinkable.Href`): the `BaseDesignerObject`s, and groups, stack panels and part references (`Group`, `Stack`, `Part`); layers cannot. A click follows the innermost link around what was clicked: its own, else that of the group, stack panel or part it is in. In the Browser, `AddNavigation` handles `MouseLeftButtonUp` on each linked element, and the innermost marks the click handled; in the Designer, the Navigate tool walks up the logical tree from the element clicked to the layer (`DesignerNavigator.DesignerNavigateClickHandler`).
- The forwarded properties are plain properties, not dependency properties. Properties no longer shows the controls (it shows their nodes), and the engine sets them from the nodes.
- `BaseDesignerObject` does not write its `Content` to XAML (`ShouldSerializeContent`), so that a control copied through `XamlWriter` and `XamlReader` gets the content its constructor builds rather than a second one. Duplicate now copies nodes, not controls.

## Text alignment

A text element (`WireFlowText`, holding a `WireFlowTextBlock`, a `TextBlock` as large as the element) places its lines across the frame with `TextAlignment` and down it with `TextVerticalAlignment`, saved as the element's `VerticalAlignment` (`Stretch`, which earlier texts have, is Top). `TextBlock` seals `MeasureOverride`, `ArrangeOverride`, `OnRender` and `OnPropertyChanged`, so the lines are moved down by the top padding: centered or at the bottom, it is the bottom padding plus the room a measuring `TextBlock` with the same font and wrapping finds left (half of it, or all). The text listens to the properties that change that room through metadata overrides in its static constructor, and to `SizeChanged`. A text shows its saved `Fill` as its background (`WireFlowEngine.TextBackground`); without one, or with one that is not a color, it is transparent, not black as `ColorUtils.StringToBrush` would make it. `WireFlowText` never has a null `Background`: none, as when it is cleared in the property grid, is coerced to Transparent, so that its whole frame can still be clicked. A text's padding is saved as its `StrokeThickness`.

In the property grid, `TextPositionPropertyEditor` is the editor of `TextAlignment` on texts and boxes (their nodes' `FlowTextAlignment`, shown by `NodeProperties`). Its row shows only where the text lies, named as the chooser names the nine positions ("Top-Left", "Top", "Center", ...), and follows `TextAlignment`, `TextVerticalAlignment` and a box's `TextHorizontalAlignment` as they change, watching them (`PropertyDescriptor.AddValueChanged`) while the row is loaded. Its "…" button, Ctrl+Enter or a double click on the value opens `Views\TextPositionDialog`: MaxServices.Core's `PagePositionControl`, the 9-point chooser of PDFTools, in a "Text position" group with OK and Cancel, as PDFTools' Add Margins and Resize Pages dialogs show it. OK sets the alignments across and down (and a box's `TextHorizontalAlignment`) through `PropertyItem.SetValue` and `SetComponentProperty`, so each change raises `PropertyValueChanged`. A text's and a box's `TextVerticalAlignment` is listed under Text.

A box's or text's `TextHorizontalAlignment` (its node's `HorizontalAlignment`: where its text lies across it) carries its `TextAlignment` (where the lines lie) with it, but for `Stretch`, so that the two stay in sync when either row is used; on a text, which is as large as its frame, the two say the same. The engine sets `TextAlignment` after it, so a saved box or text keeps the `TextAlignment` it was saved with.

## Stack panels

A stack panel (kind `stack`, `FlowStack` with a `Direction`, `Vertical` or `Horizontal`, and `Children`; on the page the `Stack` panel of Core) places its children one after another from its top left corner in its direction, as WPF's `StackPanel` does: each child keeps its size in that direction and is stretched across the panel in the other. `StackLayout.Arrange` calculates the places apart from any control. `Stack` writes each child's `Canvas.Left`, `Canvas.Top` and size across the panel when it arranges them, rather than only arranging them there, so the children keep true positions and sizes, which selection, saving, ungrouping and the Browser use as for any element; a change of direction therefore starts from the sizes the other direction gave. It arranges each child in its place at that size itself: `Canvas` would arrange it at the size it was measured at, before its size across was set, and WPF then keeps a layout clip of that older size on it, so that only that much of it shows. The panel clips its children to itself.

In the Designer, the Stack Panel tool draws one, in a faint translucent gray so that an empty panel shows; an element drawn starting inside a panel becomes its last child (the innermost panel, where they are nested). A click on a panel's child selects the child itself, unlike a group's, which selects the group; with the panel (or a group) selected, a drag that starts on a child moves the selection, and a click without a drag selects the child (`DesignerNavigator.pendingChildSelection`). Esc selects the groups and panels holding the selected elements (`SelectContainers`), and from a top-level element nothing, which shows the page. A panel's child is not moved by dragging or the arrow keys: the panel places it (`SetLeft` and `SetTop` leave it). The Outline lists a panel's children in their order and a group's topmost first, and selects any of them. Ungroup releases the children where they are.

## Outline caption

The Outline's caption has two buttons at its right end, before the pane's own menu and pin: Add Layer (`AddLayerCmd`, `DesignerNavigator.AddLayer`: a layer named `Layer<n>` above the current one, which becomes current) and Delete (`OutlineDeleteCmd`: the elements selected, else the layer chosen in the Outline, `DeleteLayer`; a page keeps one layer, and the layers of its layout are not its own). The Outline's right-click menu has the same two commands. The buttons are drawn by the docking manager's `AnchorableTitleTemplate`, a pane's title with buttons shown by the pane's `ContentId` (a `DataTrigger`); another pane's buttons go there too. They are `PaneCaptionButton`s showing tool glyphs (`PaneCaptionGlyph`, `layer-add` and `delete` among the SVGs in `Glyphs`), in the palette's `Text`, with the toolbar's frame under the mouse (`ButtonHover`, `ButtonHoverBorder`, `ButtonPressed`), and at half opacity while disabled. After an undo or redo the current layer is the top one if the one current was taken away (`KeepCurrentLayer`).

## Page keys and names

The program knows a page by its key (`FlowPage.Key`, from the repository's `Documents.Key`; not written into the page's JSON, not shown): `WireFlowEngine.Pages`, `HomePage`, `PageOfHref`, `GetPage`, `CreatePage` (which gives the key), `DeletePage`, `RenamePage` and `MovePage` take and give keys, and so do the Designer's tabs (`DesignerNavigator.PageName` holds the key), the Pages list, Navigate mode's history and the tabs kept in the settings (`PreviousTabs`; one written before keys names the page by its name, which `OpenTab` looks up). Its name is what the user sees: `WireFlowEngine.PageName` and `PageKey` go between them, the Pages list shows names through `PageNameConverter`, and a page's tab is titled with its name. Layouts are known by their keys likewise (`WireFlowEngine.Layouts`, `LayoutName`, `LayoutKey`, `GetMasterPage`, `CreateLayout`, `DeleteLayout`, `RenameLayout`; the Layouts list and layout tabs), and the New Page and New Layout dialogs offer layout names (`ILayoutListProvider.LayoutNames`). Parts are still known by their names.

A page's or layout's layout (`FlowPage.Master`, shown as Layout) names a layout by its ID or by its name: `WireFlowEngine.LayoutOf` looks for a layout with that ID, then one of that name, and `GetLayoutOf`, `InheritedPageSize`, `InheritedPageBackground` and the drawing of a page's layouts (`RenderMasterPages`) go through it. A chain of layouts that comes back to one already in it (a cycle) ends there. Properties sets a page's or layout's layout (its Layout row, `LayoutPropertyEditor`): a list of the project's layouts by name to choose one from, whose box also takes a layout's name or ID typed in, kept as typed; empty is none. A value is set as the list closes, or, typed, with Enter or as the box loses the focus; Esc takes the typing back. `MainDesignerWindow.CheckLayout` (through `NodeProperties.CheckLayout`) refuses a value that names no layout, and one that would close a circle: a layout set on itself, or on a layout that is set on it, nearer or farther. The page in front shows the layout set at once: the engine draws its layouts again under its own layers when its `Master` changes (`WireFlowEngine.RedrawLayouts`).

A layout is edited in its tab as a page is, and the pages and layouts open show it as it is being edited, before it is saved: the engine draws a layout open in a tab from that tab's DOM (`WireFlowEngine.OpenLayout`, which `MainDesignerWindow.OpenLayoutCopy` answers with a copy of it, so that the drawing never changes or follows the tab's own nodes), else from the project (`GetLayoutOf`); the size and background a page takes from its layouts come the same way. Each change of a layout tab's DOM, an undo or a redo included (`DesignerNavigator.DocumentChanged`), and the closing of its tab, schedule a refresh for when the edit is done (`ContextIdle`): every page and layout open that is set on that layout, nearer or farther (`WireFlowEngine.IsOnLayout`), has its layouts drawn again and its inherited size and background given again (`RefreshLayouts`). Layouts form a chain, never a circle. A circle is refused wherever one could be made: setting a layout (`CheckLayout`), renaming a layout or changing its ID to a name or ID that a layout under it names as its layout (`MainDesignerWindow.ClosesCircle`, through `NodeProperties.CheckLayoutReference` and `RenamePage`), and making a new layout of such a name (New Layout, `ChainNames`). Drawing still stops at a layout already in the chain, for a file that has a circle. A layout is renamed in Properties, as a page is (`MainDesignerWindow.RenamePage` takes either); a name another layout has is refused. Renaming a layout makes the `Master` naming its old name name the new one, and changing its ID makes those naming the old ID name the new one (`WireFlowEngine.RetargetMasters`, `FlowIds.RetargetMaster`), in the documents open as an edit and in the others in the project.

A page is renamed in Properties (its `Name`, no longer read-only) or in the Pages list (Rename), both through `MainDesignerWindow.RenamePage`: a name another page has, or none, is refused; the project renames it at once, its tabs and list item follow, and links naming it by its old name name the new one. Undoing a rename made in Properties gives the page's node its old name back, but the project keeps the new one until the page is saved.

## Page order

The pages are an ordered list, and the first is where the project starts (`WireFlowEngine.HomePage`): the Designer opens it with a project, and the Browser shows it first. The order is the project's `PageOrder` (the pages' keys, in the project's JSON), and `FlowProject.OrderPages` makes the order of the pages there are: those it names, in its order, then the others by name; a project never ordered has its `Home` (a key too) first, so it keeps its entry point. `SqliteRepository` gives its `Pages` in that order and writes the order at once (`SetPageOrder`), as it creates, deletes and renames pages at once, not at Save Project, and sets `Home` to the first page with it. A new page comes last; a renamed page keeps its place, as its key stays. `WireFlowEngine.MovePage` moves a page to an index.

In the Designer, the Pages caption has Move Up and Move Down buttons (`MovePageUpCmd`, `MovePageDownCmd`, drawn as the Outline's, with the `move-up` and `move-down` glyphs), and a page is dragged to its place in the list (`ListDragReorder`, which a line shows the gap of, in the list's text color); both go through `MainDesignerWindow.MovePage`, which moves the item in `Pages` so that it stays selected without opening it.

## Tool glyphs

Each tool in the Designer's Tools list has a glyph before its title. The SVGs in `WireFlow.Designer\Glyphs` are their source: line glyphs on a 24 x 24 grid, as PDFTools' toolbar icons (stroke `currentColor`, 1.7 wide, round caps and joins, no fill), made of `path`, `line`, `polyline`, `polygon`, `rect`, `circle` and `ellipse` only. `Documents\make-tool-glyphs.cs` converts them once into `WireFlow.Designer\Xaml\ToolGlyphs.xaml` (`dotnet run Documents\make-tool-glyphs.cs` from the root), a `Geometry` per glyph keyed `ToolGlyph.<file name>` and the stroke width as `ToolGlyphStrokeThickness`, merged into `App.xaml`. The Designer uses the XAML only and reads no SVG: change an SVG, or add one, and run the script again rather than editing the XAML. It checks that WPF reads each glyph and that it stays inside the grid.

The toolbar's buttons use the same glyphs (`new`, `save`, `save-all`, `undo`, `cut`, `align-left`, `same-width` and the others; see "Toolbar"), drawn by `ToolbarIconStyle`.

A tool names its glyph with `DrawingTool.Glyph` (the SVG's file name); `GlyphGeometry` finds it in the application's resources. The Tools list's template draws it 18 px square, in the row's own text color (`TextElement.Foreground`), so that it follows the theme and the selected row. The Outline draws its entries' glyphs the same way, 16 px square: each outline proxy names one (`UIElementProxy.Glyph`: a rectangle's and an ellipse's are their tools', and `layer`, `layout`, `group`, `stack-panel`, `part`, `box`, `text` and `image` the others'; `element` for a kind without one), which `ToolGlyphConverter` finds. The PNGs the proxies' `ImageSource` names are no longer shown.

## Toolbar

Under the menu, the Designer has the toolbar of PDF Workshop (PDFTools; the Organizer's `ToolbarButtonStyle` and `ToolbarIconStyle`), `MainToolbar` in `MainDesignerWindow.xaml`: flat buttons 34 x 24 px that show a frame under the mouse and are dimmed while disabled, on the window's background between two 1 px lines in the palette's `ChromeBorder`, with the palette's colors (`Text`, `Ink`, `ButtonHover`, `ButtonHoverBorder`, `ButtonPressed`, `Separator`), so that it follows the theme. Its buttons run the commands of the menus (New, Open, Save, Save All; Undo, Redo; Cut, Copy, Paste, Delete; Group, Ungroup, Bring to Front, Send to Back; the six alignments and Fill Space; Distribute Horizontally and Vertically, Make Same Width and Height; Zoom Out, the zoom, Zoom In, Fit Page), so each is enabled as its command can run, and their tooltips name the keys. Open shows PDFTools' manila folder and its name; the others show tool glyphs (see "Tool glyphs"), 18 px, in the palette's ink. The buttons take no keyboard focus, so that the keys stay with the page.

## Fill Space

Alignment → Fill Space (the main menu, the page's context menu and the toolbar, after Align Bottom; `FillSpaceCmd`, `DesignerNavigator.FillSpace`) makes each selected element fill the room around it: its edges go out to the nearest elements beside, above and under it, or to the edges of the page. `FillLayout.Fill` (Core) calculates it apart from any control, from the element's place, its container's and the places of the others, across, down or both:

- Across, an element stops the left or right edge if it lies at the element's height (they share some of it) and wholly to that side; down, likewise for the top and bottom edges. An element it overlaps does not count, as it lies under or over it (a background, a label on it); an overlap of less than half a pixel counts as touching.
- Both ways, the larger of across-then-down and down-then-across is taken, which differ where the room is not a rectangle.
- For an element on a layer, the container is the page, and the others are the elements of every visible layer, the page's own and its layouts', so a layout's header and footer take room. For a group's child, the container is the group and the others its other children. A stack panel's child is left: the panel places and sizes it.
- Several selected elements are filled one after another, in the order selected, each seeing the ones before it where they are now, so that two do not fill the same room. It is one step of Undo.

## Zoom

Each page, layout or part open has its own zoom, its `DesignerPanel`'s (`Scale`, 1 being the actual size; `Zoom` tells of each change), from 10% (`MinimumZoom`, so that Fit Page can show a long page whole) to 500% (`MaximumZoom`), rounded to a whole percent. View → Zoom In (Ctrl+=, Ctrl+numpad +), Zoom Out (Ctrl+-, Ctrl+numpad -) and Actual Size (Ctrl+Shift+0) are MaxWrite's, with its steps of 10% (`ZoomStep`); Fit Page (Ctrl+0) is PDFTools'. The toolbar ends with them as MaxWrite's does: Zoom Out, the zoom of the page in front (bound to `CurrentDesigner.Designer.Zoom`; a click is Actual Size), Zoom In, and Fit Page, with the `zoom-out`, `zoom-in` and `fit-page` glyphs (PDFTools' icons). Zoom In, Zoom Out and Actual Size keep the point at the center of the view where it is (`ZoomTo`, `ZoomBy`, `ActualSize`), and a notch of the mouse wheel zooms by a step about the point under the mouse. Fit Page (`FitPage`) zooms so that the whole page shows as large as it can with 20 px around it (`FitPageMargin`), and centers it; it is done once, not kept as the window is resized. The zoom is not kept in the settings: a tab opens at 100%.

## Navigate mode

The Designer is in Design mode or in Navigate mode (`MainDesignerWindow.IsNavigateMode`). The Navigate tool is the mode: choosing it in the Tools list enters it, and choosing another tool there leaves it with that tool (`SelectedToolIndex`, `SetNavigateMode`); F9 (`NavigateModeCmd`; F5 is Reload from File) and View → Navigate Mode switch it, leaving it with the Select tool. The toolbar's Navigate Mode toggle (PDFTools' `ToolbarToggleStyle`, tinted while on) is left out for now, by the user's decision, and kept as a comment in `MainDesignerWindow.xaml` to be put back. In Navigate mode every page, layout and part open behaves as in WireFlow Browser:

- **Links.** Each document has the Navigate tool (`NavigateModeTool`; one opened meanwhile starts with it, `ModeDrawingTool`), which deselects as it is chosen: a click follows the innermost link around what it hits, in the same tab, or brings forward the tab that shows the page already (`NavigateToPage`); a page chosen in Pages is shown in the tab too. Esc leaves Navigate mode, with the Select tool (`EscapePressed`).
- **Read-only.** Nothing is selected, the Outline selects nothing, and Properties is off; the keys of the page and most commands need a selection, and those that change a page without one (Undo, Redo, Paste, Add Layer, the Outline's Delete) are disabled.
- **Back and Forward** (the toolbar's buttons, View → Back and Forward, Alt+Left and Alt+Right) go through the pages visited since Navigate mode was entered, kept as a browser keeps them (`NavigationHistory`: a visit after going back drops the pages ahead); they show the page in the tab in front, as a link does.

- **Indicator.** A badge reading "Navigate Mode" hangs from the top edge of each document, at its center, under the tabs, with its lower corners rounded (`DesignerNavigator.ShowNavigateBadge`; the navigator's content is a grid holding the `DesignerPanel` and the badge over it). Clicks go through it to the page. Its colors are the application's `NavigateBadgeBrush` and `NavigateBadgeTextBrush`, which `MainDesignerWindow.ApplyNavigateBadgeColors` sets from the settings, so a change in Tools → Options reaches every badge open.

Leaving Navigate mode gives every document the Select tool, or the tool chosen, and forgets the history.

**Highlight Links.** View → Highlight Links (Ctrl+L), and its toggle on the toolbar after Back and Forward (`ToolbarToggleStyle`, the `highlight-links` glyph), lay a highlight over every link on the pages open: every element shown whose control has an `Href` (`ILinkable`: the `BaseDesignerObject`s, groups, stack panels and part references), at any depth, the layouts' elements included. It works in Design mode and in Navigate mode, and is kept in the settings (`ConfigSettings.HighlightLinks`; the window's `HighlightLinks`). Each highlight is a `LinkHighlightAdorner` over the element, which lets clicks through, drawn in the application's `LinkHighlightBrush`: Tools → Options' Link highlight color made partly transparent by its Link highlight opacity (`LinkHighlightColor`, `LinkHighlightOpacity`; `MainDesignerWindow.ApplyLinkHighlightBrush`). A navigator lays them again once each change is done (`DesignerNavigator.ScheduleLinkHighlights`, at `ContextIdle`): when its DOM changes or is replaced, when its elements change, when its layouts are drawn again, and when its tab comes to the front (a tab behind has no adorner layer).

## Esc

Esc returns to the Select tool wherever the keyboard is, and in Navigate mode leaves the mode (`MainDesignerWindow.EscapePressed`). A class handler of `Window`'s `KeyDown`, registered once (`RegisterEscape`), takes it from the Designer's window and from its floating panes (`LayoutFloatingWindowControl`, windows of their own), handled or not, so that a control that uses Esc itself (a list ending a rename, a drop-down closing) does so and the tool still changes. A key binding of the window would miss both. The page's own Esc (ending a drag, selecting the containers) runs as before.

## Window and panes

The Designer comes back as it was closed: the window's place and size (`ConfigSettings.Left`, `Top`, `Width`, `Height`; maximized or minimized, the place it goes back to, `RestoreBounds`) and whether it is maximized, set in the constructor before the window shows (`ApplyConfigSettings`); a place no longer on any screen is left to Windows. The panes, docked, floating, auto-hidden or hidden, with the sizes their splitters give them, are the docking manager's layout, kept as XML in `ConfigSettings.DockLayout` (`DockLayoutSerializer`, the fork's `LayoutSerializerBase` writing its DTOs with `XmlSerializer`) and restored in `Window_Loaded` before any tab opens (`RestoreDockLayout`). The layout names each pane by its `ContentId` (`tools`, `pages`, `layouts`, `parts`, `images`, `history`, `outline`, `properties`) and gives it back its content, so every pane needs an ID of its own; a pane with an ID the saved layout lacks is dropped. The layout read replaces the layout objects, so the window finds its document pane again (`DocumentPane`); a saved layout without one, or one that cannot be read, gives way to the layout built in. Tabs are not kept in the layout: the previous project's tabs reopen through `PreviousTabs` (see "Options").

Each pane can be hidden (`CanHide`; none can be closed): its caption's X hides it, and the View menu, under Theme, lists every pane, checked while it shows, in the order of `PaneOrder`; choosing one hides or shows it (`LayoutAnchorable.Hide`, `Show`), and a pane shown again goes back where it was. The items are made each time the menu opens (`ViewMenuItem_SubmenuOpened`), from the panes in the layout and its hidden ones (`Layout.Hidden`), since restoring a saved layout makes the panes again. A pane hidden stays hidden in the layout saved, so the Designer starts with it hidden.

## Changes not saved

A page, layout or part with changes not saved (`DesignerNavigator.IsModified`, which raises `ModifiedChanged` as it changes) is shown as MaxPad shows its documents: its tab has a 7 px dot after its name, in MaxServices.Core's `TabStripItem` color (`#C05A00`; the `DocumentHeaderTemplate`, by the tab's `DesignerNavigatorDocument.IsModified`); the window's caption has an asterisk after the project's name while any document open has changes not saved (`DesignerTitle`); and the status bar says Modified or Saved of the one in front (`DocumentState`). File → Save (Ctrl+S, and the toolbar's Save, `SaveFileCmd`) saves the document in front only, as its draft, and is on while it has changes. File → Save All (Ctrl+Shift+S, and the toolbar's Save All after Save, `SaveAllCmd`, on while a project is open), which this file calls Save Project, saves each document open with changes and then commits the project as a new revision (`SqliteRepository.SaveProject`). File → Save As copies the project to another `.wf` file (`SqliteRepository.SaveProjectAs`: SQLite's backup of the whole file, drafts, archive and images included, into `<name>.wf.tmp`, then moved into place), goes on with that file, and saves there as Save All does (`MainDesignerWindow.SaveProjectFileAs`); the file the project was in keeps what it had, and the edits not yet saved go into the new file only. Save, Save All, and Yes when the Designer asks as it closes, save each document as what it is (`DesignerNavigator.SaveCurrentDocument`, by the tab's `Kind`): a layout saved as a page would become a page of its name, which is how a page named `NormalLayout` came to be in `Data/WireFlow.wf`.

Nothing with changes not saved is closed without asking. A tab closing (its X, or any `Close`) asks Save / Don't Save / Cancel for its page, layout or part (`MainDesignerWindow.DocumentClosingHandler`, on each tab's `Closing`): Yes saves it as what it is (its draft, which Save Project makes the saved version), No drops the changes, Cancel keeps the tab open. Closing the project, as New, Open, Reload from File and Close do (`CloseProject`), asks once for the project, as closing the window does, and Cancel stops the command; it then closes the tabs without asking each (`closingProject`). Every such question goes through `AskYesNoCancel`, a `MessageBox` that a script hosting the window answers instead.

## Options

Tools → Options… is the Options dialog of MarkdownTools' and PDFTools' programs: `OptimaxTools.Options` 1.0.0, Optimax's own library made in Optimax.Shared.Lib, kept as a package in `LocalPackages\` as MaxServices.Core is. It has no look of its own, so it takes the theme's controls; `Views\DesignerOptionsDialog` derives from it, gives it the theme's colors, and adds the groups of options and their options. OK sets the dialog's results, which `MainDesignerWindow.OptionsMenuItem_Click` puts in `ConfigSettings` and saves; the dialog changes nothing itself. A new option is a setting in `ConfigSettings`, a control in the dialog's constructor, read in its `Apply`, and applied by the window.

- Files → Reopen the previous project at startup (`ConfigSettings.ReopenPreviousProject`, off by default): `SaveConfigSettings` keeps the project open as the settings are saved, as the Designer closes, in `PreviousProject` (null when none is open), with the tabs of the main document pane in `PreviousTabs` (kind and name, in order) and the one in front in `PreviousTab`. `Window_Loaded` opens it again once the window shows, if it is still there (`ReopenPreviousProject`), without its home page, and reopens the tabs whose page, layout or part it still has; with none, its home page.

- Drawing → Return to the Select tool after drawing an object (`ConfigSettings.SelectAfterDrawing`, off by default): once a tool has drawn an object (`DesignerNavigator.ElementDrawn`, raised when `CreateShape` put one on the page), the window chooses the Select tool, as Esc does (`SelectDefaultTool`), after the mouse is let go.

- Properties → Highlight the row being edited (`ConfigSettings.HighlightSelectedProperty`, on by default) and Highlight color (`SelectedPropertyColor`: null for the Windows accent, else `#AARRGGBB`), a list of named colors, partly transparent so that the text shows in every theme, as PDF Workshop offers its focus frame's colors; a color typed into the settings file is offered as Custom.

- Navigate Mode → Link highlight color and Link highlight opacity (`ConfigSettings.LinkHighlightColor`, blue `#FF1E88E5` by default, and `LinkHighlightOpacity`, 0.35): the highlight View → Highlight Links lays over links (see "Navigate mode"); the opacity is a list, with one typed into the settings file offered as Custom.

- Navigate Mode → Indicator color and Indicator text color (`ConfigSettings.NavigateBadgeColor`, orange `#FFE8590C` by default, and `NavigateBadgeTextColor`, white).

  These four values belong to the project: its pages' colors decide which colors show on them. A project keeps its own in its `FlowProject` JSON (`NavigateBadgeColor`, `NavigateBadgeTextColor`, `LinkHighlightColor`, `LinkHighlightOpacity`; null where it has none, as a project made before them), and the window uses the open project's, else the Designer's (`MainDesignerWindow.NavigateBadgeColorInUse` and the others; `ApplyNavigateColors` as a project is opened, made or closed). With a project open, Options shows and sets the project's, which `SaveProjectSettings` writes into the file at once, as the page order is written; with none open, it sets the Designer's, in `ConfigSettings`, and a new project starts with those as its own (`NewProject`). The page says which it is.

  The three colors of Navigate Mode are color rows (`DesignerOptionsDialog.ColorRow`): a button showing the color as a swatch and as `#AARRGGBB`, which opens the color dialog (`ColorPickerDialog`, with its swatches and the colors chosen last) on it. OptimaxTools.Options has no such row, so each is made as a list's row, for its words and its place, and its button takes the list's place once the dialog has laid out its rows (`PlaceColorButtons`, after `Finish`). A color the settings file holds that cannot be read starts from the default.

The settings file is not offered for editing from the dialog (no Edit Settings File button): the Designer writes it as it closes, so edits made to it while the Designer runs would be lost.

## Project file format

A project is one SQLite database file, `<name>.wf`, written by `SqliteRepository`. `PRAGMA application_id` is `0x57464C57` ("WFLW") and `PRAGMA user_version` the format number, now 3; a file with another application id or another format number is not opened. A format 2 file is upgraded to 3 in place, in one transaction, as it is opened (`SqliteRepository.UpgradeToFormat3`): each document gets a key, and the project's page order and home page name keys; a build from before format 3 cannot open it afterwards. The format 1 files, whose JSON named .NET classes, were upgraded once with `Documents\upgrade-wf-to-format-2.cs`, which can upgrade any other format 1 file left (`dotnet run upgrade-wf-to-format-2.cs -- <file.wf> ...`). The format has four tables:

- `Project` — one row: the `FlowProject` JSON (size, background, home page, the order of the pages, the Navigate mode colors, `RevisionNo`). The order and the colors are written at once (`SetPageOrder`, `SaveProjectSettings`); the rest at Save Project.
- `Documents` — one row per page, layout and part (`Key`, `Kind` `page`, `layout` or `part`, and `Name`): `Key`, the primary key, is the document's own, a GUID of 32 hex digits without hyphens or braces (`SqliteRepository.NewKey`), which never changes and is never shown; `Name` is what the user calls it, unique within its kind, and may change. `Saved`, the JSON of the saved version, and `Draft`, the JSON of the unsaved edits. `SavePage`, `SaveLayout` and `SavePart` write the draft. `SaveProject`, in one transaction, raises `RevisionNo`, archives the project and the saved version of each document that has a draft under the new revision, and makes the drafts the saved versions.
- `Archive` — earlier versions (`Kind`, which can also be `project`, `Name`, `RevisionNo`, JSON, and the document's `Key`): the version that the save of that revision replaced, under the name it had.
- `Images` — imported images (`Name`, the file name, and `Data`).

Names compare ignoring case, as file names did. Each document stays one JSON value rather than a table per element type: the element model is open-ended (an element's `Type` names its kind), and the programs read and write whole pages. A page and a layout are read with their drafts, so that a layout's edits show on the pages set on it before Save Project; a part is read in its saved version only. Renaming a part is not implemented, since elements refer to it by name; deleting or renaming a page or layout leaves its archived versions under the old name.

Each operation opens the file and closes it again: pooling is off, so the file is not held open between operations, and the Browser can view a project the Designer is editing. A new or converted file is built under a temporary name (`<name>.wf.tmp`) and then moved into place.

JSON is written and read by Newtonsoft.Json with `FlowJson.Settings` (in `WireFlow.Repository.Folder`, used through `FlatFolderRepository.SerializeToJSON` and `DeserializeFromJSON`), and names no .NET types:

- An element's `Type` is its kind, and chooses its class when it is read (`FlowElementConverter`): `group` is `FlowGroup`, `stack` (a stack panel) `FlowStack`, `part` (a part reference) `FlowPart`, `image` `FlowImage`, and `box`, `text`, `rect` and any other kind `FlowElement`. A new kind of element with a class of its own needs its kind added to `FlowElementConverter.Create`. A part document is read as `FlowPart`, a page or layout as `FlowPage`, the project as `FlowProject`.
- Enums are written by name; NaN, an automatic size, as `null`.
- Every value is written, defaults included, so reading never depends on the defaults in the code: changing `FlowElement.Defaults` or a constructor changes new elements only.
- `Type`, `Name` and `Id` come first in each object. `Id` came after format 2 without a new format number: a file written before has none, which reads as null, and an older build drops the key.
- Unknown keys are dropped on load and are therefore lost on the next save.
- A page's or layout's `Width` and `Height` are its own size, or `null` when it takes the size of its nearest layout that has one, else the project's (`WireFlowEngine.InheritedPageSize`). In the Designer, Properties shows the page's size with no element selected, its own or the inherited one (`NodeProperties`); a size set there becomes the page's own, unless the page has none and it is the inherited size.
- A page's or layout's `Background` is likewise its own color, or `null` when it takes the background of its nearest layout that has one, else the project's (`WireFlowEngine.InheritedPageBackground`). Properties shows the page's own background, empty when it has none; a background set there becomes its own, and one cleared makes the page follow its layout or the project again. `RenderPage` gives the canvas the page's background, so the Designer and the Browser show it alike.

**Folder projects.** The earlier storage, `FlatFolderRepository`, keeps a project as a folder: `<name>.project` (the `FlowProject` JSON); `pages/*.page`, `layouts/*.master` and `parts/*.part`, with unsaved edits in `*.new` files beside them; `pages.archive/` and the other `*.archive/` folders, holding `<name>.<revision>` files; and `images/`. When the Designer opens a `.project`, `SqliteRepository` converts it into `<name>.wf` beside it, writing every document again in the current JSON, and opens that; the folder is left as it is. If that `.wf` file already exists, it is opened, not replaced. The Browser opens `.wf` files only and says so when given a `.project`. The sample projects in `Data` are `.wf` files only. `optimax-old.wf` is a 2016 project migrated once from an earlier format still (`Optimax.wireflow`, elements named only by `Type`, without `$type` tags), which no storage reads.

## Known traps

- **Inside the `OptimaxTools.*` namespaces, `Dock` is the namespace `OptimaxTools.Dock`, not WPF's `Dock` enum.** C# finds the namespace, a member of `OptimaxTools`, before the `using System.Windows.Controls` of the file, so `Dock.Top` does not compile there, and a file-level `using` alias does not help. Write `System.Windows.Controls.Dock.Top`, as the fork does, when merging upstream code.
- **WPF's Fluent theme restyles every window shown without a style.** Merging `Fluent.Light.xaml` or `Fluent.Dark.xaml` into the application's resources turns the Fluent theme on (`Application.ThemeMode` reads Light or Dark), and a window shown with no `Style` of its own then gets Fluent's `Window` style, even when an implicit style of its type exists. The docking windows lost their templates that way: dragging a floating pane crashed in `OverlayWindow.OnApplyTemplate`, and a floating window showed Fluent's plain frame. A `Window` subclass that needs its own template sets `SetResourceReference(StyleProperty, DefaultStyleKey)` in its constructor, as those of OptimaxTools.Dock now do.
- **Scratch programs that host the Designer's window.** Creating `App` queues its `Startup` handler, which opens a real Designer window as soon as the dispatcher runs and applies the saved theme. `MainDesignerWindow` also writes its settings (`%APPDATA%\WireFlow\WireFlow.Designer.config`) when it closes. Remove the `Startup` handler, and keep a copy of the settings file to put back.
- **Single-file `dotnet run app.cs` scripts default to `PublishAot=true`,** which disables dynamic code generation, unlike the apps. Add `#:property PublishAot=false` to scripts that load WireFlow documents, so that Newtonsoft.Json runs as it does in the apps.
- **`dotnet publish` into an existing folder copies a file only when it is newer than the one there.** After a package downgrade, the publish succeeds but keeps the newer DLLs of the old version. Publish into an empty folder, as `publish-locally.bat` does.
- **Visual Studio's design-time builds share `obj/` with command-line builds.** A command-line build while the solution is open in Visual Studio can fail with CS2001 (a missing `*.g.cs`); building again succeeds.
- **Line endings.** The repository has `core.autocrlf=true` and no `.gitattributes`: the index holds LF, the working tree CRLF. Git Bash `sed -i` rewrites a CRLF file as LF; run `unix2dos` on it afterwards.
- **Microsoft.Data.Sqlite 9.x brings SQLitePCLRaw 2.1.10,** whose `lib.e_sqlite3` NuGet flags with a high-severity advisory (NU1903, GHSA-2m69-gcr7-jv3q). Microsoft.Data.Sqlite 10.0.14 brings 2.1.13, which is not flagged. Keep the NuGet audit warnings visible when upgrading it.
- **`DesignerPanel` lives in Core, but the `DesignerBackgroundBrush` and `PageFrameBrush` resources exist only in the Designer.** It refers to them with `SetResourceReference`, which leaves them unset where they are missing, so the Browser can host it; the Browser sets `Background` and `PageFrameBrush` from the palette itself.
- **The Designer's Outline follows the page's elements only when told.** `MainDesignerWindow.PopulateOutlineTree` brings it up to date in place (`OutlineSync`) on navigation, on a tab switch, and when the current `DesignerNavigator` raises `ElementsChanged`: the entries of the elements that stay are kept, the same objects, so their items keep their state, and only those of elements added, removed or moved change. A new `DesignerNavigator` operation that adds, removes or reorders elements must call `OnElementsChanged()`, or the Outline goes stale. An entry follows its element's node by itself (`UIElementProxy.Node`), so a rename shows at once; `Detach` lets the node go as the entry leaves. The tree virtualizes (Standard mode: Recycling would hand an item's expanded state to another entry), and its items are expanded by its `TreeViewItem` style, not by walking them. Its entries' `IsHighlighted` follows the current designer's `SelectedElements`: `UpdateOutlineHighlight` runs on `SelectionChanged` and after each rebuild, so a change of selection must raise `SelectionChanged` even when `CurrentElement` stays, as `DeselectElement` does.
- **A `Button` with a `Style` of its own still takes the system theme's black `Foreground`.** The explicit style replaces Fluent's implicit one, but WPF's own theme style of `Button` (Aero2) still sets what the explicit style leaves unset, `Foreground` among them, so a glyph that takes its color from the button (`TextElement.Foreground`) was black, and lost on a dark caption. A style of a button set by key gives it a `Foreground` (the palette's `Text`), as `ToolbarButtonStyle` and `PaneCaptionButton` do.
- **A property grid editor gets the grid's implicit styles.** A `PropertyEditor` that creates a `TextBox`, `CheckBox` or `ComboBox` gets the grid's compact style, not the theme's; give a control a `Style` of its own to look otherwise.
- **A WPF `ListBox` reports a cleared selection as `SelectedIndex` -1.** Code that indexes `Items` with it must check the range.
- **A list of keys shown through a converter (Pages, Layouts, `PageNameConverter`) does not show a rename by itself.** Replacing an item with the same key string kept the old name and left two items selected; `RenamePage` refreshes the list's view instead (`CollectionViewSource.GetDefaultView(list).Refresh()`), which keeps the selection. `EditableListBox.CommitEdit` ends the edit before it runs what the edit does, so that a list drawn again meets no edit in progress.
- **.NET Framework's `System.Drawing.Icon` skips PNG-compressed icon images,** such as the 256 px images of the application icons, so Windows PowerShell cannot load them that way. Check a built exe with the shell's `PrivateExtractIcons` instead.
- **WPF properties in Properties can break the Designer.** The grid lists every browsable property of the WPF element selected. `Panel.IsItemsHost`, set on a page panel (`BaseElement`'s subclasses, `DesignerCanvas`), makes WPF refuse access to its children, and the next click crashed. Such a property is hidden by a `new` property marked `[Browsable(false)]` that forwards to the base one.
- **A `StaticResource` that no dictionary holds throws when the XAML is loaded,** not when it is built: a window or dialog that names a removed style crashes the Designer only as it opens. The image dialog (`SelectImageDlg`) named the implicit `Panel` style of the theme before Fluent, so placing an image crashed. Look for the keys a XAML names (`{StaticResource {x:Type ...}}` included) when a theme's dictionaries change.
- **An element without a `Type` is read as a `FlowElement`,** and shown as an unknown object: the kind lives only in `Type`.
